Regulatory design sketch · Draft for discussion

Separate certification for authorization and data services

§170.315(g)(10) certifies an EHR's authorization machinery and its clinical data API as one inseparable module. This sketch splits certification into two module types — authorization and data — using SMART on FHIR as it exists today. An organization designates one authorization service; other systems certify as data modules against it. A PACS, for example, can become certified health IT in its own right: surfacing its imaging catalog over FHIR, serving the underlying studies over DICOMweb, and participating in the organization’s unified authorization.

Josh Mandel · August 2026 · Builds on §170.315(g)(10) and SMART App Launch

1The problem

The (g)(10) criterion certifies one Health IT Module that both runs SMART App Launch authorization — registration, consent, refresh tokens, revocation, introspection — and serves the US Core data API. Nothing in SMART requires this coupling: the discovery document already lets a FHIR endpoint point its authorization endpoints anywhere. The coupling is a certification artifact.

A PACS holding a patient's imaging has no certification path of its own. It can honor the EHR's tokens through introspection — which (g)(10)(vii) already requires the EHR to offer — but that arrangement rests on out-of-band agreement: the certification program gives it no test procedure and no guarantee that a deploying organization can configure it.

2The proposal

Refactor (g)(10) to certify two module types:

  • An Authorization module: registration, SMART App Launch, consent, refresh tokens, revocation, and token introspection — plus the ability for the deploying organization to configure external resource servers — authorizing them as introspection clients, listing them as associated_endpoints in the discovery document, and granting the scopes they rely on.
  • A Data module: serves its data — the clinical FHIR API, or another surface such as imaging's FHIR + DICOMweb — enforcing authorization as an introspection client of a configurable authorization server.

The data module is a role, not one product. The US Core clinical API required today is one instance; an imaging module serving ImagingStudy over FHIR and studies over DICOMweb is another; further kinds can follow. The interface the authorization module offers is the same for all of them — an organization can attach any conformant data service, certified or custom.

Both capabilities may certify together as a single Health IT Module — how EHR products ship today. Inside such a module the two halves may remain coupled however the vendor likes, and its data half is not required to work with any other authorization server. The authorization half still carries the configurable-resource-server obligations, because those face outward.

Or the modules certify separately. A standalone data module demonstrates conformance against a reference authorization server; an authorization module demonstrates conformance against a reference data service.

Apps are untouched either way: register once with the organization's authorization server, authorize once, and use the token at every location it covers. SMART's experimental Authorization Details for Multiple Servers (authorization_details, RFC 9396) lets one grant carry per-location scopes and patient context.

3Interface requirements

The boundary between the two module types is three things that already exist: SMART discovery, SMART v2 scopes, and token introspection. The token is the assertion; the introspection response is its validation — and SMART's introspection profile already requires the response to carry scope, client_id, exp, and any launch context (such as patient) granted with the original token.

4Regulatory changes required

Four changes, none requiring a new standard:

  1. Restructure (g)(10) into two separately certifiable capabilities — authorization services and data services. A vendor may still certify both together as a single Health IT Module. A standalone data module is tested against a reference authorization server; a standalone authorization module, against a reference data service.
  2. Require organization-configured resource servers. The authorization capability — standalone or within a combined module — must let the deploying organization authorize external resource servers as introspection clients and list them as associated_endpoints, on fair terms under §170.404.
  3. Require scope support for attached data. The authorization flow — request, patient consent, grant, introspection — must work for SMART v2 scopes over any FHIR resource type (patient/ImagingStudy.rs as readily as patient/Observation.rs), not only the certified base data set. The Certification Companion Guide already permits scoping non-USCDI resources as patient/[Resource]; this generalizes that allowance into an obligation. Organizations SHOULD also be able to register custom scope strings, with display text for the consent screen, for data a resource-type scope cannot describe.
  4. Adopt authorization_details via SVAP once the multi-server grant surface stabilizes.

No HL7 changes are needed. SMART's token introspection profile already requires the response to include scope, client_id, and exp, plus any launch context (such as patient) granted with the original token. Where ONC wants more — for example, guaranteeing fhirUser for user-scoped tokens — the Certification Companion Guide already articulates requirements above the base specifications, and can do so here.

5Case study: imaging

SMART Imaging Access (Argonaut) is a working data module: it lists a patient's studies as FHIR ImagingStudy resources, serves the underlying data over DICOMweb (WADO-RS), validates the EHR's tokens by introspection, and is discovered through associated_endpoints. Its scope needs are met by an ordinary SMART v2 resource scope, patient/ImagingStudy.rs. What it lacks is regulatory footing — under this split, a PACS vendor gets a test procedure to certify against, and a deploying organization gets the right to attach the result.

The net effect: the EHR's authorization server becomes the organization's authorization server — one registration, one consent, for everything the organization attaches.
